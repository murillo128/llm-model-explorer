# Codex Epic Scheduler

## Responsibility

Use this skill only when the controlling parent issue declares `execution_mode: epic-dag`. GitHub issues, labels, the canonical epic-DAG comment, and the canonical execution-context comments are the persistent source of truth. Each invocation reconstructs current state from GitHub, performs at most one bounded scheduling transition, and terminates; it does not depend on memory from an earlier turn.

The scheduler has two phases:

1. **first invocation:** turn the compact parent seed into one durable canonical DAG, initialize the integration branch when needed, then schedule the first eligible wave;
2. **later invocations:** consume that same canonical DAG and schedule one new eligible wave from current child labels.

It owns scheduling metadata and activation only. It never implements children, audits pull requests, resolves technical conflicts, integrates accepted work, closes children, completes the parent, or moves the default branch.

## Parent seed contract

The parent issue body contains one fenced YAML seed. The seed deliberately names the work set but does **not** precompute dependency edges or mutexes:

```yaml
execution_mode: epic-dag
integration_branch: codex/epic-issue-3
max_parallel_workers: 4
child_issues: [10, 11, 12, 13]
```

Required fields are:

- `execution_mode: epic-dag`;
- `max_parallel_workers`, a positive integer;
- `child_issues`, a non-empty list of unique positive issue numbers from the same repository.

`integration_branch` is optional in the seed. When omitted, use `codex/epic-issue-<parent-number>`. The first invocation may create the resolved integration branch from the exact current default-branch head when it does not already exist. After the canonical DAG is published, its `integration_branch` is authoritative and the scheduler never recreates, rewrites, rebases, merges, or otherwise advances that branch.

The seed is bootstrap input only. It is not the live DAG after initialization.

## Entry and workflow state

Load `AGENTS.md`, the parent issue, this skill, `codex-github-operations`, and only the child issues/comments needed by the active phase. Confirm repository and issue identity.

The parent must have exactly one workflow-state label:

- first invocation: `execution-ready`;
- later invocation: `in-progress`.

A first-run parent with an already published canonical DAG is an inconsistent retry unless the canonical graph can be verified as the exact durable result of an interrupted initialization. Reconcile only unambiguous interrupted state; otherwise return to design authority rather than generating a second graph.

An `in-progress` parent with no canonical DAG is invalid. Do not infer a graph from current labels or regenerate silently.

## First invocation: generate the DAG

### 1. Validate the seed and child set

Before mutation, require one unambiguous seed and verify:

- `child_issues` contains unique positive issue numbers and does not contain the parent;
- every child issue exists in the same repository and is an issue rather than a pull request;
- every child has exactly one official workflow-state label;
- every child has a self-contained technical contract sufficient to determine whether another declared child is a prerequisite and whether concurrent execution would contend on a serialization-sensitive mutable surface;
- no declared child is merely a duplicate/superseded issue unless the parent explicitly intends it to participate.

Children may already be `completed`. Fully designed children waiting for this epic should normally be `queued`. `blocked`, `design-required`, and `investigation-required` are allowed in the graph but remain manual states and are never promoted automatically.

### 2. Derive direct dependencies

Read all declared child contracts before choosing edges. Add `A` to child `B`'s `depends_on` only when `B` cannot be implemented, validated, or integrated correctly without the accepted result of `A`.

Prefer explicit technical evidence: required APIs/data formats, generated artifacts, migrations, integration prerequisites, accepted contracts, or an explicit child-to-child dependency. Do not create an edge merely because two issues are related, touch nearby code, share a theme, or would be convenient to order.

Keep the graph minimal: record **direct** prerequisites, not redundant transitive edges. If `C` requires `B` and `B` requires `A`, do not also add `A` to `C` unless `C` independently requires `A`'s result.

When a material dependency cannot be determined safely from the child contracts, fail closed before publishing the DAG and move the parent to `design-required` only when that unresolved decision genuinely requires design authority. Do not guess an ordering just to make the graph acyclic.

### 3. Derive mutexes

Mutexes serialize otherwise dependency-independent children that must not execute concurrently because they own the same mutation-sensitive resource or integration surface. Examples include a shared schema migration, generated registry, package/release metadata, or a subsystem whose concurrent edits would make safe integration non-local.

Use stable repository concepts for mutex names such as `schema`, `packaging`, or `runtime-core`; never issue numbers, worker IDs, branch names, or ad-hoc timestamps. Do not use mutexes as a substitute for genuine dependencies, and do not serialize children merely because both may touch a common file if their work is safely parallelizable.

### 4. Validate the generated graph

Before publishing anything, normalize the proposed graph with each child's current observed state and validate it with `skills/codex-epic-scheduler/scripts/plan_wave.py` when practical. Fail closed unless:

- every seed child appears exactly once and no other child appears;
- every dependency refers to a declared child, never itself;
- every mutex is a non-empty unique string for that child;
- the graph is acyclic;
- `max_parallel_workers` remains a positive integer;
- the resolved integration branch name is valid.

The pure planner validates structure and deterministic wave selection; it does not certify that semantic dependency choices are correct. The scheduler must separately check those choices against the child contracts before publication.

### 5. Initialize the integration branch

Resolve `integration_branch` from the seed or default naming rule. If it exists, use its current exact head. If it does not exist, use `codex-github-operations` to create it from the exact current default-branch head and verify the new ref. Never overwrite an existing branch, and never force a ref to repair an unexpected branch state.

### 6. Publish and verify the canonical DAG

Search parent comments for the canonical marker immediately before publication. With zero matches, create exactly one canonical DAG comment. If another writer published one after planning, re-read it and accept it only when it is structurally valid and exactly represents the same declared child set; otherwise fail closed rather than overwriting it.

After publication, re-read the comment and verify its marker, child set, dependencies, mutexes, worker limit, and integration branch. Only then replace the parent's `execution-ready` state with `in-progress` while preserving unrelated labels.

The durable canonical comment must exist **before** the parent becomes `in-progress`, because later child label events discover the active parent through that comment.

## Later invocations: validate current canonical state

On every later invocation, read the single canonical DAG and every declared child's current workflow-state label. Validate again that:

- the parent is `in-progress`;
- the canonical graph has one non-empty integration branch and positive worker limit;
- the integration branch still exists;
- children are unique positive issue numbers in the same repository;
- every child has exactly one official workflow state;
- dependencies remain closed, unique, non-self, and acyclic;
- mutex entries remain non-empty strings unique within each child.

Do not compare the live graph to a newly inferred graph and do not regenerate it from edited child prose. Once initialized, graph changes require explicit design-authority repair of the canonical DAG.

## Observable state classification

For slot accounting, use only each child's single current workflow-state label:

- `queued`: schedulable when dependencies are satisfied;
- `execution-ready` or `in-progress`: active and consuming one slot;
- `review-ready`, `completed`, `blocked`, `design-required`, or `investigation-required`: not consuming a scheduler slot.

Only `completed` satisfies a dependency. `review-ready` does not. Ordinary dependency waiting is `queued`, never `blocked`.

If active children already meet or exceed `max_parallel_workers`, select nothing.

## Deterministic wave selection

A child is a candidate only when its state is exactly `queued` and every issue in its `depends_on` list is exactly `completed`.

Calculate `available_slots = max(0, max_parallel_workers - active_children)`. Collect mutexes held by active children. Inspect candidates in ascending issue-number order and greedily select a candidate only when a slot remains and none of its mutexes is held by an active or already selected child.

Do not maximize cardinality by skipping an earlier compatible candidate for a different combination. Ascending issue number is the only tie-breaker.

Use the bundled pure planner when practical to make the decision inspectable.

## Canonical child execution context

Immediately before applying a non-empty wave:

1. re-read the parent canonical DAG and all child workflow-state labels; recompute if anything changed;
2. resolve the canonical integration branch's current exact 40-character head SHA once as `base_sha`;
3. use that same `integration_branch` and `base_sha` for every child selected in the wave.

Each selected child must have exactly one top-level execution-context comment identified by:

```text
<!-- codex-execution-context:v1 -->
```

Its fenced YAML is:

```yaml
epic_issue: 3
integration_branch: codex/epic-issue-3
base_sha: 0123456789abcdef0123456789abcdef01234567
```

With zero matches, create it. With one match, update that same comment in place. With more than one, fail closed for that child. Verify the durable context before making `execution-ready` observable.

A reactivated child receives an updated canonical comment. Child issue prose remains authoritative for technical scope but is not authoritative for execution base/PR target while one valid execution-context comment exists.

## Apply one wave

For each selected child in ascending order:

1. re-read its state;
2. if it is no longer exactly `queued`, skip it without mutating labels;
3. publish/update and verify canonical execution context;
4. replace `queued` with `execution-ready` while preserving unrelated labels;
5. verify the resulting sole workflow state is `execution-ready`.

If context publication succeeds but the label transition races/fails, leave the child non-executable. A later invocation can update the same comment and retry safely. Do not fill a newly available slot after the chosen wave begins; a later event recomputes from GitHub.

## Wake-up model and termination

The repository's single issue-state dispatcher wakes the parent when a declared child receives `completed` or is deliberately returned to `queued`. Duplicate/delayed wake-ups are safe because every invocation recomputes from current GitHub state and canonical comments.

After first-run initialization and/or the selected wave is verified, terminate. If no candidates qualify, terminate successfully with the parent still `in-progress`. Even when every child is `completed`, do not close, complete, audit, or integrate the parent; final epic acceptance is a separate explicit workflow decision.

Report only the phase (`initialized` or `scheduled`), validated child count, active count, available slots, selected issue numbers, integration branch and wave `base_sha` when applicable, skipped races, and any exact fail-closed defect. Do not emit the full DAG again when it is already preserved canonically.
